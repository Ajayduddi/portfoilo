## Work requiring production access

1. **Apply response headers at the actual host.** Use the exact generated `dist/security-headers.json` from the deployed build. The HTML CSP protects resource loading, but `frame-ancestors`, framing protection, MIME sniffing controls and Permissions-Policy require server headers. Confirm HTTPS/redirects, then introduce HSTS with a short initial lifetime before increasing it; do not enable `includeSubDomains` or preload without checking every subdomain. Recheck all routes/resources after deployment. [MDN CSP guidance](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/CSP).
2. **Enforce webhook validation in n8n/the proxy.** Accept POST JSON only for `/portfolioEmail`; cap the body at 32 KiB and validate the same required strings and lengths (name 100, email 254, subject 200, message 5000). Reject invalid email/control characters with a fixed 400 response before invoking email nodes. Reject wrong content types with 415 and oversized bodies with 413. Use a fixed sender/recipient and validated email only as Reply-To. Send plain text or escape every user field in HTML. Keep SMTP/provider credentials in server credentials.
3. **Add abuse controls before email dispatch.** Configure per-client rate limits and return 429 with Retry-After; choose limits using actual traffic and shared-IP behavior. Trust forwarding headers only from the known proxy. If rate limits are insufficient, add a bot challenge with server-side verification, a server-only secret, action/hostname checks and replay/expiry checks. A browser-side secret, hidden webhook URL or CORS policy does not authenticate callers.
4. **Restrict CORS and redact errors.** Once the live origin is confirmed, allow that origin and approved local development origins, with only the required methods/headers. Use fixed error responses and avoid exposing workflow details, credentials or stack traces. Keep GET content endpoints public only for data intentionally displayed by this portfolio. Set success only after the workflow accepts the message for processing, and return a failure when it cannot accept it.
5. **Verify n8n's own security and maintenance.** Check the running version/advisories, editor authentication, TLS/proxy settings, credentials storage, restricted administrative access and retention of contact payloads/execution logs. No running n8n version or server configuration has been verified from this repository. [n8n security documentation](https://docs.n8n.io/hosting/securing/overview/).
6. **Run deployment acceptance checks.** Check real response headers and image loads without posting a message. Use a mocked/staging email node for invalid-input, oversized-body, rate-limit and bot-challenge cases. Send a real contact message only with explicit owner authorization. Re-run both dependency audits regularly; remove overrides only after confirming the resulting lockfile stays patched.

No live n8n workflow was inspected or changed during the repository review.
